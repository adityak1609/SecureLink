SecureLink Secure Multimedia Communication

ISL project synopsis
Aditya Khanna · Registration number 240911662 · V IT · Section B
Manipal Institute of Technology · Manipal Academy of Higher Education
Guides Dr Snehal Samanth and Dr Anup Bhat

SecureLink implements and evaluates authenticated multimedia communication between a client terminal and a bank-server simulation. It supports text, images, audio and video, integrates traffic analysis and PCAP conversion, and demonstrates five security goals through implemented controls and reproducible experiments.

Objective

Design and evaluate a secure multimedia framework between two physical or simulated endpoints using mutual authentication, authenticated encryption, replay rejection, accountable audit records and bounded recovery after communication failures. Measure communication efficiency and validate security behaviour using attack tests and captured traffic.

Problem statement

An unsecured channel exposes transaction content and media to interception, alteration and impersonation. Replaying a valid request can duplicate an action, interrupted connections create uncertainty about completion, and an editable local log provides weak evidence of what happened. A compact academic framework should address these problems together and distinguish tested behaviour from unsupported security claims.

Scope and implementation

The Python implementation transfers UTF-8 text, PNG/JPEG images, WAV/MP3 audio and MP4 video. Authenticated 64 KiB chunks support upload and download with a 32 MiB file limit. Receiver-side persistence records each accepted offset, permitting reconnection and resume. A final SHA-256 verifies the complete file before successful completion. Safe basenames and media format metadata preserve usable received files.

The banking scenario uses synthetic identity media and a simulated transaction ledger. A device-scoped request ID makes repeated submissions idempotent: the same transaction cannot be committed twice under the same ID. No real accounts, balances, identity verification, regulatory compliance or financial transfers are claimed.

Approved ISL modules

Traffic Analysis uses Wireshark/TShark and PyShark to inspect captured communication and report descriptive traffic statistics. PCAP Analysis converts captures to SQLite and XML and verifies matching record counts. The automated demonstration records actual socket bytes in a clearly labelled USER0 PCAP. A separate network-capture path supports real IP/TCP captures when an appropriate capture driver is installed.

Experimental method

The demonstration uses separate client, bank and witness processes over loopback as simulated devices. Actual media is uploaded, downloaded, hash-checked and decoded. Controlled tests alter ciphertext and headers, replay encrypted records, submit invalid credentials and oversized requests, interrupt connections and modify audit logs. Tests run with isolated state.

Efficiency evaluation compares actual secured and plaintext lab transfers with identical chunking and audit policy. Thirty observations per media type and mode follow a discarded warmup, with alternating execution order. Metrics include median and p95 completion latency, useful throughput, process CPU time, sampled resident memory, handshake time and protocol bytes. The separate recovery experiment measures reconnection after a lost completion acknowledgement.

Threat model and limitations

Network attackers and attackers able to modify the bank log are considered. Device secrets, application code, transaction database and independently protected witness state are trusted. Shared-secret compromise does not preserve past confidentiality; forward secrecy and third-party non-repudiation are outside the implemented scope. The witness must run under independent protection for anchored-prefix tamper detection. Loss of the witness intentionally stops accountable completion.

The same-host experiments do not establish physical isolation, congested-network performance, resistance to arbitrary denial of service or financial-system readiness. The measured CPU and memory values are aggregate process observations. High entropy and absence of known text in a capture support inspection but do not prove cryptographic security. A LAN replication requires the documented two-device setup and capture driver.

Requirements and deliverables

The tested environment is Windows 11 with Python 3.14.3. Dependencies include cryptography, PyShark, psutil, Pillow, FFmpeg via imageio-ffmpeg, Matplotlib and pytest. Linux deployment is supported by the socket-based design but has not been measured in this run. Two networked computers or simulated endpoints are required; three processes provide the client, bank and witness roles.

Deliverables comprise source code, valid synthetic media, attack tests, a repeatable separate-process demonstration, PCAP captures, SQLite/XML exports, measured benchmark data and charts, a protocol/threat-model specification and this synopsis. See the evaluation report and setup instructions.
